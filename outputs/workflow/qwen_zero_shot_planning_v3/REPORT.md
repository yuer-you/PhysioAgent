# Qwen 多步规划提示词 v3

## 结论

提示词 v3 在同一组 20 条开发/集成样例上只通过 **14/20（70%）**，相比 v1 的 95% 和 v2 的 90% 均明显回归。v3 不能作为后续默认提示词。

## 指标

| 指标 | 结果 |
|---|---:|
| 合法计划 | 15/20（75%） |
| 计划严格匹配 | 14/20（70%） |
| 执行成功 | 15/20（75%） |
| 参考检查通过 | 14/20（70%） |
| 回答有工具结果依据 | 15/20（75%） |
| 端到端成功 | 14/20（70%） |

## 失败模式

- `wf_filter_stats_003`、`wf_filter_stats_004`：遗漏关闭 `steps` 数组的 `]`。
- `wf_load_stats_001`、`wf_load_stats_002`、`wf_load_stats_003`：同样遗漏 `]`。
- `wf_single_002`：计划是合法 JSON，但把单步 `detect_peaks` 错误扩展成了 `detect_peaks -> calculate_heart_rate`。

20 条输出均未触及 128-token 上限，因此这些错误不是生成长度截断。

## 决策

停止基于这 20 条开发样例继续堆叠提示词规则。v3 的结果说明，更多自然语言自检并不等于更可靠的结构化输出，还可能干扰原本正确的工具选择。

后续保留全部原始实验结果：

- v1：19/20，格式稳定，但默认列语义错误 1 条。
- v2：18/20，默认列语义已修复，但两条 JSON 遗漏 `]`。
- v2 + 256 token：仍为 18/20，排除长度截断。
- v3：14/20，自检提示导致明显回归。

工程上优先使用 v2 的参数语义，并增加可审计的保守恢复层：只修复能够唯一确定为“缺少一个 `steps` 数组右括号”的输出，同时分别报告严格成功率和恢复后成功率。这样不会篡改原始模型成绩，也能提高实际 Agent 的可用性。

离线验证表明，在 v2 的两条非法输出中分别只在最后一个 `}` 前插入 `]` 后，JSON 均可解析，而且计划与人工期望严格一致。因此该恢复规则在当前错误模式上是唯一且可验证的，不需要猜测工具名或参数。
